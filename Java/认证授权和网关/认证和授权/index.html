    认证和授权：hhjava 的标准认证链¶

    阅读路线：先理解第 1～3 节，再做第 10 节“不联网的密码认证练习”，最后对照第 4～9 节阅读 hhjava。你不需要先把 OAuth2 所有参数背下来，才能理解用户名密码是怎样验证的。

    基础词语表¶

    词语 是什么，在这里做什么
    Spring Security Spring 生态的安全框架，提供认证、授权和常见 Web 防护的组件，不是用户数据库
    用户与客户端 用户是登录的人；客户端是代表用户调用接口的 App/网站，也可能是独立后端程序；client_id 不是用户名
    凭据（credentials） 证明身份的材料，例如密码、令牌；用户自己声称的 ID 不是证明
    权限（authority）、角色（role） 权限表达可执行的能力，角色是一种业务身份分组；项目把数据库角色名作为权限字符串使用
    RBAC（Role-Based Access Control，基于角色的访问控制） 给用户分配角色，再根据角色限制能力；仍可能需要检查具体对象归属
    OAuth 2.0 让客户端获得有限 API 访问权限的授权框架；不单靠它定义用户身份登录结果
    OIDC（OpenID Connect） 在 OAuth2 之上增加身份层，以 ID Token 等规范告诉客户端用户身份
    SPA（Single-Page Application，单页应用） 主要在浏览器执行前端代码的网站；H5 在这里泛指移动浏览器网页，不是另一个后端微服务
    PKCE（Proof Key for Code Exchange，授权码交换证明密钥） 客户端先提交随机值的摘要，换 Token 时再提交原值，证明兑换者持有本次请求的校验材料
    BFF（Backend for Frontend，服务于前端的专用后端） 由受控后端管理浏览器应用的令牌等逻辑；不是当前项目自动已有的前端服务
    JWT（JSON Web Token） 按标准携带一组声明的令牌格式；本项目用 RSA 私钥签名，不是把密码加密后发给前端
    RSA / RS256 RSA 是非对称密码算法；RS256 是本项目采用的 RSA + SHA-256 签名算法标识，私钥签名、公钥验证
    JWKS（JSON Web Key Set） JSON 格式的密钥集合；本项目对外只公布验证签名所需的公钥信息，不公布 RSA 私钥
    claim / issuer / audience claim 是令牌声明；issuer 表示签发者，audience 表示预期使用令牌的资源方；简称分别为 iss、aud
    scope 客户端获得的授权范围，如允许某类 API；它和数据库角色不是同一个概念
    Session / Cookie Session 是服务端保存的会话状态；Cookie 是浏览器保存并在匹配条件下自动携带的数据，常包含会话标识
    CSRF（Cross-Site Request Forgery，跨站请求伪造） 利用浏览器自动携带凭据诱导发请求的攻击；CSRF Token 用于校验请求来源上下文，不是 Access Token
    SSO（Single Sign-On，单点登录） 在多个受信应用间利用已有登录状态减少重复输入密码，不等于复制各服务私钥
    JDBC（Java Database Connectivity） Java 数据库连接接口；这里授权记录通过 JDBC 保存在数据库，以便后续读回

    上表用于读懂后文。协议角色、授权码、ID Token 与 Access Token 的详细区别见 OAuth2/OIDC 学习笔记。

    1. 认证与授权的区别¶

    认证（Authentication）回答“你是谁”，授权（Authorization）回答“你可以做什么”。密码正确只完成身份核验，不代表可以删除任何用户的文件。

    例如：登录确定你是 alice；scope、角色和文件所有权规则共同决定 alice 能否操作某个备份。接口只写 authenticated() 时，只要求请求已有可信身份，并没有自动完成对象所有权校验。

    协议基础见 OAuth2/OIDC 学习笔记，请求参数与 Reqable 步骤见 注册与登录。本文解释当前源码如何分工，不重复整套协议教程。

    2. 当前项目的混合模式¶

    调用方 入口 用户如何认证
    第一方原生 App /auth/mobile/login/password JSON 接口 原生页面收集用户名密码，user 服务执行标准密码认证
    纯浏览器 Web/H5/SPA OAuth2 Authorization Code + PKCE，可使用 OIDC 浏览器跳转 user 登录页，表单认证后继续授权流程
    可信后端客户端 OAuth2 Client Credentials 校验外置客户端 secret；不代表某个用户

    表中是 user 内部路径，经项目约定的网关路由访问时加 /user。公开浏览器客户端不保存 secret；有受控服务端的 Web 应用应按机密客户端或 BFF 设计。

    移动 JSON 接口是第一方专用业务协议，不是 OAuth2 Password Grant。入口不同，但 user 是唯一的 RSA Access Token 签发方；资源服务只通过 JWKS 获取公钥。

    3. Spring Security 中的几个角色¶

    类型 初学者理解方式 当前职责
    AuthenticationManager 认证任务入口 接收待认证的凭据并交给 Provider
    DaoAuthenticationProvider 用户名密码认证执行者 调用用户加载服务，再用编码器匹配密码
    UserDetailsService 账号资料加载器 根据普通用户名查询数据库，不比较密码
    PasswordEncoder 密码哈希与匹配工具 注册时编码，登录时由 Provider 校验 BCrypt
    UserDetails 认证需要的账号资料契约 提供用户名、密码哈希、权限和账号状态
    Authentication 一次认证的输入或结果 成功结果包含 principal 和权限
    principal 被认证的主体 密码登录为 AuthenticatedUser；JWT 资源请求通常为 Jwt
    SecurityContext 框架保存当前认证结果的上下文 供后续授权使用，不是业务用户表或 Token 数据库

    标准 DaoAuthenticationProvider 本来就负责协调 UserDetailsService 和 PasswordEncoder，项目只需要提供正确的账号加载与配置，不必在 Controller 或 Service 再比较一次密码。Spring Security 官方认证链说明

    4. 按调用顺序读源码¶

    第一步：请求只携带真实业务参数¶

    移动端 MobileAuthController 用 PasswordLoginRequest 接收 username、password，通过 @Valid 校验后调用 MobileAuthService。

    浏览器表单也提交普通用户名和密码，但还必须携带 CSRF Token 和会话 Cookie。不要把 JSON、手机号认证类型或角色编码到 username 字符串中。

    第二步：把密码核验交给共享 Provider¶

    WebSecurityConfig 创建共享的 PasswordEncoder 和 DaoAuthenticationProvider。浏览器过滤链注册该 Provider；移动端 Service 注入基于该 Provider 显式构建的 AuthenticationManager。

    共享的是同一个密码 Provider 和编码器，不应假定浏览器过滤链内部的 AuthenticationManager 与移动端注入的是同一个实例。

    移动端调用的关键语句：

    Authentication authenticated = authenticationManager.authenticate(
        UsernamePasswordAuthenticationToken.unauthenticated(
                request.username(), request.password()));

    unauthenticated(...) 表示“这里有待验证的凭据”，不是“用户名提交上来就可信”。

    第三步：查询用户和角色¶

    CustomUserDetailsService.loadUserByUsername 调用 UserService.getUserByUsername。Service 先查询用户，再调用 RoleMapper.findRolesByUserId，用一条参数化 JOIN 取得角色。

    角色查询通过 user_role 关联 role，使用 distinct 去重。无角色返回空列表，不需要在 Service 中先查询关联 ID，再组装 ID 集合去查询角色。完整 SQL 和 XML 对应关系见 Mapper 数据库访问层。

    第四步：返回带稳定 ID 的认证身份¶

    用户加载服务把数据库结果转换成 AuthenticatedUser：

    // loadUserByUsername 中的返回语句节选。
return new AuthenticatedUser(user.getId(), user.getUsername(), user.getPassword(),
        userAuthorityMapper.grantedAuthorities(user));

    它实现标准 UserDetails，补充数据库 userId。这个 ID 来自数据库，不由 App 提交；权限也从数据库角色转换，不信任客户端自报角色。

    DaoAuthenticationProvider 用数据库哈希验证输入密码。用户不存在和密码错误对外使用同一失败提示；数据库不可用等基础设施故障则应返回服务错误，不能伪装成用户输错密码。

    第五步：复用结果，不再重复查询¶

    移动认证成功后，MobileAuthServiceImpl 要求 principal 为 AuthenticatedUser，调用其 toTokenUser() 生成不含密码的用户 DTO，用于创建会话和统一签发 JWT。

    这是复用本次认证已经拿到的可信身份，不是跨请求缓存用户。若 Provider 返回不符合契约的主体，按服务端装配错误处理，不回退到按用户名再查询一遍。

    收益是减少重复数据库读取，并确保本次认证与签发使用同一份用户 ID、用户名和角色快照。密码认证仍沿用标准框架链路，接口参数和 JWT 的 sub 没有因此变成 userId；当前用户令牌的 sub 仍是用户名。

    5. 密码擦除与授权记录持久化¶

    AuthenticatedUser 中密码哈希只供当前认证使用：

    • 实现 CredentialsContainer，成功认证后由框架调用 eraseCredentials() 置空。
    • 密码字段使用 transient，getter 使用 @JsonIgnore，分别约束 Java 序列化与 Jackson JSON。
    • JDBC 授权记录通过明确的 @JsonCreator 恢复用户 ID、用户名、权限，不恢复密码。
    • 权限集合做防御性复制且不可修改，避免外部修改原列表而改变认证结果。
    • 当前账号表没有锁定、禁用或到期字段，对应状态方法返回 true。未来增加这些规则时，需要把数据库状态映射进去，不能只添加字段不改认证。

    OAuth2 授权记录使用框架的 JDBC 持久化机制。自定义 principal 需要支持写入与读回，并保持已有标准 Spring Security 用户记录的读取兼容性；不能为绕过反序列化错误而开启任意类型支持。详细原因见 序列化。

    擦除 principal 的密码哈希不代表 Java 进程中所有字符串副本都已安全清零，也不允许记录请求原始密码。

    6. 移动端会话与刷新边界¶

    MobileAuthServiceImpl 创建高熵随机 Refresh Token，数据库只存摘要。一次密码登录创建一个会话家族；刷新轮换 Token，旧 Token 重放撤销整个家族，退出也按家族幂等撤销。

    刷新不能只复用首次登录的角色快照：它通过当前会话中的 userId 再加载账号和角色。用户已删除则撤销家族并拒绝刷新，角色变化用于新令牌。

    这些行为不会立即撤销已签发的 Access JWT。资源服务独立验签，不会因为 JWT 有 sid 就每次回查移动会话表。

    7. 两类登录如何统一签发和授权¶

    RsaKeyConfiguration 管理 RSA/JWKSource/JwtEncoder；JwtAccessTokenPolicy 集中维护 RS256、kid、audience 和权限等共同规则；移动端 RsaMobileAccessTokenIssuer 复用统一编码器与策略。

    Web/OIDC 令牌还包含框架按协议生成的内容，并不要求两类令牌每个 claim 都相同。关键是签发身份、受众和资源授权约定一致。

    资源服务器同时验证签名算法、issuer、audience 和时间声明：

    • scope 映射成 SCOPE_<scope>。
    • 数据库角色以原名写入 authorities，不自动加 ROLE_。
    • 对当前角色使用 hasAuthority 等匹配方式；不要无条件改成依赖 ROLE_ 前缀的 hasRole。
    • Client Credentials 表示服务客户端，不附带某个用户的角色。

    网关职责见 网关、过滤器与拦截器。

    8. 浏览器会话、CSRF 与 SSO¶

    授权码流程先在浏览器建立短期登录 Session，再继续授权并换 Token。user 不能全局改成无状态或关闭 CSRF；注册和三个已定义的无状态移动 JSON POST 端点才做精确豁免。

    多个已注册客户端可以利用同一授权服务器上的有效浏览器登录会话减少重复登录，这才是理解 SSO 的起点。它不等于所有服务共享用户表、共享 RSA 私钥或直接共享 App Refresh Token。

    浏览器 OIDC 退出与移动会话退出是两种不同操作，不能互换。具体端点见 注册与登录。

    9. 按什么顺序实现和验证¶

    学习或重新实现时，依次完成：账号与角色查询 → 共享编码器和 Provider → AuthenticatedUser 及密码保护 → 两种入口复用认证 → 统一签发 → Refresh Token 轮换 → 独立资源验签 → 错误处理和测试。

    在 hhjava 根目录运行 mvn -pl hhjava-service/hhjava-user -am test，重点验证密码正确/错误、无角色/多角色、避免二次查询、principal 密码擦除与 JDBC 读回、刷新重放和退出。

    真实 MySQL/Flyway 与浏览器授权码登录仍需独立环境验收。手机号验证码、微信和 Apple 登录尚未实现；扩展时应按各自可信凭据设计 Provider 和账号绑定规则，不能直接相信客户端传入的手机号或第三方用户 ID。

    10. 动手：先验证密码，不接 JWT 和数据库¶

    目标：亲自观察“加载账号 → 校验密码 → 返回身份和权限”。先完成 Spring Boot 入门练习，在 Mac 的独立 hhjava-learning-basics 中操作。本练习只运行测试，不开放登录端点，不更改 hhjava 的安全链，也不需要 Nacos、MySQL 或 RSA 密钥。

    10.1 添加测试依赖¶

    在学习工程 pom.xml 现有 <dependencies> 内追加：

    <dependency>
    <groupId>org.springframework.security</groupId>
    <artifactId>spring-security-core</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.springframework.security</groupId>
    <artifactId>spring-security-crypto</artifactId>
    <scope>test</scope>
</dependency>

    版本由 Boot 3.3.7 父 POM 管理，构造器按这一基线编写；不是要求你把不同版本文档的配置 API 混用。test 范围只对测试可见，不给前面 /hello 接口自动加登录页。IDEA 重新加载 Maven。

    10.2 创建完整认证测试¶

    文件：src/test/java/com/example/learning/PasswordAuthenticationTest.java

    package com.example.learning;

import java.util.UUID;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.security.authentication.BadCredentialsException;
import org.springframework.security.authentication.ProviderManager;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.authentication.dao.DaoAuthenticationProvider;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertNotEquals;
import static org.junit.jupiter.api.Assertions.assertNull;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.junit.jupiter.api.Assertions.assertTrue;

class PasswordAuthenticationTest {
    private final PasswordEncoder encoder = new BCryptPasswordEncoder();
    private String rawPassword;
    private ProviderManager manager;

    @BeforeEach
    void prepareOneLearningAccount() {
        // 每次测试临时生成，不是项目账号密码，也不打印原文或哈希。
        rawPassword = UUID.randomUUID().toString();
        UserDetails user = User.withUsername("learning-user")
                .password(encoder.encode(rawPassword))
                .authorities("book:read")
                .build();
        InMemoryUserDetailsManager users = new InMemoryUserDetailsManager(user);
        DaoAuthenticationProvider provider = new DaoAuthenticationProvider(encoder);
        provider.setUserDetailsService(users);
        manager = new ProviderManager(provider);
    }

    @Test
    void shouldAuthenticateAndEraseCredentials() {
        Authentication result = manager.authenticate(
                UsernamePasswordAuthenticationToken.unauthenticated("learning-user", rawPassword));

        assertTrue(result.isAuthenticated());
        assertEquals("learning-user", result.getName());
        assertTrue(result.getAuthorities().stream()
                .anyMatch(authority -> authority.getAuthority().equals("book:read")));
        assertNull(result.getCredentials());
        assertNull(((UserDetails) result.getPrincipal()).getPassword());
    }

    @Test
    void shouldRejectIncorrectPasswordAndUnknownUser() {
        assertThrows(BadCredentialsException.class, () -> manager.authenticate(
                UsernamePasswordAuthenticationToken.unauthenticated("learning-user", rawPassword + "x")));
        assertThrows(BadCredentialsException.class, () -> manager.authenticate(
                UsernamePasswordAuthenticationToken.unauthenticated("missing-user", rawPassword)));
    }

    @Test
    void shouldUseSaltAndMatchesInsteadOfComparingTwoHashes() {
        String firstHash = encoder.encode(rawPassword);
        String secondHash = encoder.encode(rawPassword);
        assertNotEquals(firstHash, secondHash);
        assertTrue(encoder.matches(rawPassword, firstHash));
        assertTrue(encoder.matches(rawPassword, secondHash));
    }
}

    @BeforeEach 在每个测试前准备独立账号；InMemoryUserDetailsManager 用内存资料代替数据库，只是练习的 UserDetailsService。User 是框架实现的账号资料类型，不是 hhjava 的数据库 User 实体。book:read 是教学权限，不会自动变成当前项目的角色。

    10.3 运行并检查¶

    在学习工程根目录执行：

    mvn -Dtest=PasswordAuthenticationTest test

    预期 BUILD SUCCESS。这同时验证：正确密码产生可信认证结果；错误密码和未知用户都失败；认证结果中的凭据被擦除；同一密码每次 BCrypt 编码通常不同，但 matches 都能验证。

    若找不到 Security 类，检查依赖是否加载、测试是否误放进 src/main/java。若数据库密码认证失败，不要直接调用 encode(input).equals(storedHash)；应该让共享 Provider 调用 matches。

    10.4 将实验对应回项目，而不是重写认证逻辑¶

    学习工程内存账号                 hhjava 数据库账号
InMemoryUserDetailsManager  →  CustomUserDetailsService
框架 User                   →  AuthenticatedUser（增加稳定 userId）
两者都经过 ProviderManager → DaoAuthenticationProvider → PasswordEncoder

    认证成功返回 Authentication，这一步既没有自动签发 JWT，也没有因为直接调用 authenticate 就自动把结果保存到浏览器 Session。浏览器过滤链继续管理上下文和会话；移动端 Service 继续创建自己的 Refresh Token 家族并调用统一签发器。

    Servlet 安全链通常在一次请求内通过 SecurityContextHolder 暴露身份，并在请求结束后清理线程关联；是否跨请求保存取决于安全链和上下文仓库配置。不能自己设置一个全局静态“当前用户”，否则不同请求会混在一起；WebFlux 则使用响应式上下文，不直接复制线程绑定方案。

    至此再回到第 4 节读实际调用链：需要替换的是“从哪里加载账号”和“认证成功后做什么”，不是在 Controller 中重新实现 BCrypt、JWT 或多套密码规则。

    11. 验证码和其他登录方式先学什么¶

    这是基础概念与后续设计边界，不是当前 hhjava 已有的接口。

    • 图形/交互验证码主要用于增加自动化滥用成本，不能单独证明某个账号归你所有；校验材料应由服务端关联本次挑战，并限制有效期、尝试次数和重用。
    • 手机短信验证码属于 OTP（One-Time Password，一次性密码）的一种使用形式，主要证明本次能接收某号码的消息；发送、校验、失效、限流与账号绑定是不同步骤，不能只判断“输入了六位数字”。
    • 微信、Apple 登录要由后端按提供方协议验证凭据并完成本地账号关联，不能信任客户端直接传来的第三方用户 ID。
    • MFA（Multi-Factor Authentication，多因素认证）结合不同类别的证明材料；密码加上同一密码的另一种编码不是第二个因素。

    扩展前先写清“凭据从哪里来、谁验证、是否只能用一次、对应哪个本地账号、失败如何防滥用”，再选择 Provider 或独立验证组件。现有注册、密码验证、JWT 签发规则不应因此复制成多套。
