# OMP Advisor：用第二个模型检查测试是否有效

Advisor 是 OMP 的后台顾问。主模型负责开发和运行测试，顾问用独立上下文检查工作记录、读取相关代码，再把发现反馈给主模型。适合检查需求遗漏、实现偏差和测试是否覆盖真实问题。

本文依据《我给 AI 配了个监工，它当场抓到假测试》整理，操作按 **OMP 18.22.2** 核对。[视频来源](https://www.douyin.com/video/7707660556873780522)

## 1. 如何发现无效测试

视频介绍的案例中，主模型修复代码并新增测试，1020 个测试全部通过。顾问发现测试走的是 `record_event` 路径，会丢弃与缺陷有关的 `schema_version` 字段，因此修复前后都能通过。

开发者随后改用能保留该字段的 `backfill` 路径，并重新引入旧缺陷，确认新测试会失败。验证回归测试时，应检查三件事：

- 测试是否经过实际出错的入口，保留触发缺陷所需的数据。
- 同一个测试是否在旧实现上因原缺陷失败，在修复后通过。
- 失败原因是否确实来自目标行为，而非依赖缺失、编译错误或环境故障。

旧实现的验证可以放在临时工作树中进行，记录提交 SHA、测试命令和结果。

## 2. 顾问如何工作

启用后，Advisor 按设定频率接收主会话新增记录，包括工具调用、执行结果和输出，必要时读取相关代码。默认工具为只读的 `read`、`grep`、`glob`，修改仍由主模型完成。

| 反馈级别 | 用途 |
| --- | --- |
| `nit` | 小问题或改进建议，在后续边界交付 |
| `concern` | 影响正确性的风险、方向偏差或遗漏约束 |
| `blocker` | 继续执行会产生错误结果或明显浪费工作时，发出高优先级纠偏意见 |

独立上下文让顾问从另一视角检查工作，但它仍会读取过程记录，默认也可能包含主模型的推理。它会维护自己的历史，并非每轮清空上下文。

**`blocker` 通过消息影响主模型。** 默认主模型不会等待顾问追完全部进度，已执行的命令也不能被反馈撤回。提交、推送等交付步骤应安排在最终评审和测试验收之后。[工作机制与反馈规则](https://github.com/can1357/oh-my-pi/blob/v18.22.2/docs/advisor-watchdog.md)

## 3. 开启与关闭

准备好 OMP，以及主模型和顾问模型可用的连接。在目标项目目录运行 `omp`，然后操作：

1. 输入 `/model`，进入 **Roles → advisor**，明确选择顾问模型。模型角色的分配与顾问的启用是两个步骤，详见[模型角色配置](模型角色配置.md)。
2. 在 OMP 对话框逐条输入：

   ```text
   /advisor on
   /advisor status
   ```

3. 确认已开启且模型正确，再发送开发任务。过程中阅读反馈卡片，处理发现或说明依据。
4. 任务结束后用 `/advisor status` 查看顾问状态、token 用量和费用，用 `/advisor off` 关闭。

已选好顾问模型时，也可以在终端用 `omp --advisor` 启动带顾问的会话。`/advisor on` 对当前会话生效。[启用方式](https://github.com/can1357/oh-my-pi/blob/v18.22.2/docs/advisor-watchdog.md#enabling-the-advisor)

## 4. 模型搭配与成本

主模型与顾问可以来自不同供应商。可先让成本较低的模型负责实现，再让擅长推理和审查的模型担任顾问，根据实际发现的问题和调用费用调整。

默认单顾问关闭，开启后的审查模式为 `turn`、间隔为 `1`。主模型的工具调用循环也属于工作回合，因此一次用户任务可能触发多次审查。

| 需求 | `reviewMode` | `reviewInterval` |
| --- | --- | --- |
| 尽早发现偏差 | `turn` | `1` |
| 降低审查频率 | `turn` | `3` |
| 主模型准备交付时复核 | `agent-end` | `1` |

在项目的 `.omp/config.yml` 中合并以下配置，即可每三个符合条件的更新审查一次。期间新增的记录会累积到下次审查。

```yaml
advisor:
  reviewMode: turn
  reviewInterval: 3
```

若只在交付时复核，将两项改成表中的 `agent-end` 和 `1`。多顾问使用 `WATCHDOG.yml` 时，各顾问单独配置频率。费用取决于模型价格、上下文和审查次数，以 `/advisor status` 为准。[频率配置](https://github.com/can1357/oh-my-pi/blob/v18.22.2/docs/advisor-watchdog.md#watchdogyml)

## 5. 开发与验收示例

以“注册信息无效时显示错误，并且不发送注册请求”为验收条件，开启 Advisor 后可给主模型以下任务：

> 检查注册表单、提交回调和网络调用的实际路径。复现无效输入仍发请求的问题，补充验证错误提示及请求次数为零的回归测试。在旧实现上确认测试因该缺陷失败，修复后重跑。如果无法复现，说明证据。交付时给出提交 SHA、测试路径、命令和结果，并处理 Advisor 提出的发现。

使用 Codex CLI 开发时，可以另开 OMP 会话进行独立验收。向 OMP 提供验收条件、代码版本和测试日志，等 Codex 停止修改后，在相同代码版本上核对测试入口、断言及运行结果。并行开发时使用固定提交和独立工作目录，流程见[多 Agent 终端工作流](../Agent/智能体开发新需求.md)。

OMP 内置 Advisor 跟随所在 OMP 会话。独立 OMP 会话需要显式交接 Codex 的结果，子 Agent 的顾问也需要按实际任务配置。

## 6. 相关思路

视频还介绍了两种顾问机制，可用于理解不同实现方式：

- **Advisor Models 论文**研究训练小模型，为具体任务生成建议，指导参数保持不变的黑盒模型。[论文](https://arxiv.org/abs/2510.02453)
- **Anthropic Advisor Tool**由执行模型按需请求顾问，收到建议后继续工作。视频中的性能提升来自该工具的特定评测，不能直接当作 OMP 的收益预期。[Anthropic 说明](https://claude.com/resources/articles/the-advisor-strategy)

OMP Advisor 则在开启后，按配置的节奏后台审查工作记录。选型时关注需要的是按需求助、随程审查，还是交付时独立验收。
