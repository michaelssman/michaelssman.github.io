# OMP Advisor：用第二个模型检查测试是否有效

OMP 的 **Advisor，即后台顾问模型**。主模型负责改代码和运行测试；Advisor 用独立的上下文查看新增的工作记录，必要时读取相关代码，再向主模型指出问题。它适合帮你盯住一件具体的事：**这次交付的证据，真的能证明需求被满足了吗？**

## 1. 视频里的“假测试”假在哪里？

有说服力的验证是：让新测试在**旧实现上因为原缺陷失败**，再在**修复后的实现上通过**。实际项目可以在临时工作树里验证，不必动当前工作区。

## 2. 第一次使用：只为当前任务开启

1. **选择顾问模型。** 在 **OMP 对话框**输入 `/model`，进入 **Roles → advisor**，选择模型。分配角色可以保留供以后使用，但不等于已经开启审查。如果不指定，18.20.0 会尝试 `slow` 角色或内置的慢模型优先列表。参见[模型角色配置](模型角色配置.md)和[官方模型说明](https://github.com/can1357/oh-my-pi/blob/v18.20.0/docs/models.md)。
2. **启用并确认。** 在 OMP 对话框依次输入以下两行，分两次回车：

   ```text
   /advisor on
   /advisor status
   ```

   确认状态显示已开启，并且模型是你要用的，再发任务。任务结束后可再查一次状态，查看顾问用量和费用信息；输入 `/advisor off` 关闭。以后若已选好模型，也可以在终端用 `omp --advisor` 直接启动一次带顾问的会话。

## 3. 在 Java / Flutter 项目里怎么用

主模型和审查模型可以分属两个工具。选择哪种方式，取决于你希望模型**边开发边提醒**，还是**开发完再独立验收**：

| 用法 | 审查者能看到什么 |
| --- | --- |
| OMP 主模型开发，内置 Advisor 随程审查 | 同一个 OMP 会话的工作记录、工具结果和相关代码。两种模型可以来自不同供应商，只需开一个 OMP 窗口 |
| Codex CLI 开发，OMP 独立审查 | 同一个 Git 工作树里的代码、未提交的改动，以及你给 OMP 的验收条件。OMP 不会自动收到 Codex 的对话或命令输出 |

### 3.1 在同一个 OMP 会话里开发和审查

**推荐从注册流程的一项验收条件开始。** 例如你希望“注册信息校验失败时，页面留在原处，显示字段错误，不发送注册请求”。如果只断言“屏幕上出现错误文字”，即使后台仍然发出了请求，测试也可能通过。开启 Advisor 后，可以把下面这段作为任务发给主模型：

> 检查 Flutter 注册页在输入无效时是否仍会发送注册请求。先找出表单、提交回调、网络调用三者的实际路径。写一个能观察请求次数的测试，同时验证字段错误提示和请求次数为零。如果确有缺陷，先记录旧实现在这个断言上的失败，再做最小修复并重跑；如果没有复现，直接说明，不要编造修复。交付时给我测试路径、运行命令和关键结果。不要提交或推送，等我审核。

**你验收时看三样：** 测试有没有走真实的提交回调；旧实现失败的原因是不是这次要修的问题；修复后同一个测试是否通过。Java 后端也可以用同样的方法，例如检查“验证码已过期时，注册接口是否仍创建用户”。如果任务只是调整字号、间距或配色，直接看修改前后的界面通常更有效。

如果从 [app-management 多 Agent 工作区](OMP.md)派任务，注意**给主会话开 Advisor，不等于给每个子 Agent 都开了顾问**。想先熟悉这个功能，可以直接在负责改动的仓库开一次会话。已有的 `reviewer` 则适合在交付时独立核对完整差异。

### 3.2 用 Codex CLI 开发，让 OMP 独立验收

在 Herdr 打开两个标签页，进入**同一个 Git 工作树**：一个运行 `codex`，另一个运行 `omp`。可以分别执行 `git rev-parse --show-toplevel`，确认输出的路径相同。

以同一个 Flutter 注册问题为例，两边可以这样交接：

1. **给 Codex CLI：**「修复注册信息无效时仍发送请求的问题，补上回归测试。完成后给出测试命令和结果，先不要提交或推送。」
2. **等 Codex 停止修改，再给 OMP：**「验收条件：注册信息无效时显示字段错误，注册请求次数为零。请检查当前工作树，包括暂存、未暂存和未跟踪的新测试。确认测试确实经过提交按钮的回调并验证了请求次数。可以运行测试，不要修改文件。列出发现、证据和没验证到的地方。」
3. **你做决定：** 若 OMP 发现问题，把具体发现交回 Codex，修完后再复核；验收通过后再决定是否提交或推送。

## 4. 审查频率与“叫停”的边界

默认情况下，Advisor 没有开启。开启后，默认单顾问按主模型的工作回合审查，工具调用过程也可能触发审查；不是用户发一条消息就只多调用一次。若希望降低成本，可按下表在**目标项目的 `.omp/config.yml`** 中设置 `advisor` 字段；有同名配置时合并，不要覆盖其他设置。

| 适用场景 | 默认单顾问的配置 |
| --- | --- |
| 希望尽早发现跑偏，例如修改注册校验 | 默认 `reviewMode: turn`、`reviewInterval: 1`，无需额外配置 |
| 任务较长，想少审几次 | 在 `advisor:` 下设 `reviewMode: turn` 和 `reviewInterval: 3`，每三个符合条件的更新审一次 |
| 只想在主模型准备交付时复核 | 使用下方示例；这不会在中间每次调用工具时审查 |

```yaml
advisor:
  reviewMode: agent-end
```

**视频里的“叫停”是顾问提出严重问题，不是禁止推送的权限开关。** 默认顾问以只读方式检查，主要用 `read`、`grep`、`glob`；主模型默认也不会一直等顾问追完进度。顾问的反馈不能撤回已经执行的命令。如果你只负责最终审核，就把“给出证据，等我决定是否提交”写进任务，并把推送保留为独立步骤。详细行为见 [OMP 18.20.0 Advisor 设置](https://github.com/can1357/oh-my-pi/blob/v18.20.0/docs/settings.md#advisor)及[顾问工具与审查时机](https://github.com/can1357/oh-my-pi/blob/v18.20.0/docs/advisor-watchdog.md)。
