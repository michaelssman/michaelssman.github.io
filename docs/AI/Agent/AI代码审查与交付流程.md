# AI 代码审查与交付流程

本文结合《AI 写的代码谁来审？Anthropic 的七道关卡》与 Claude Code 团队实践整理，按一次代码合并请求（PR）的生命周期说明用法。[视频来源](https://www.douyin.com/video/7708203711163632896) · [官方实践](https://claude.dev/blog/solving-code-review-at-anthropic/)

## 1. 七个环节

| 环节 | 要做什么 | 核对重点 |
| --- | --- | --- |
| 开发者自证 | 运行相关测试和构建，界面改动提供截图，并交给新上下文的 Agent 再看一次差异 | 需求是否满足，测试是否经过真实路径 |
| AI 代码审查 | 检查逻辑与边界，对候选问题再次核实，过滤误报 | 文件位置、触发条件、影响与证据，区分新增问题和原有问题 |
| 独立安全审查 | 检查权限、注入、敏感数据和其他安全边界 | 是否存在实际可利用的风险 |
| 自动检查 | 由 CI 执行格式、静态分析、类型检查、测试和构建 | 必需检查失败时阻止合并 |
| 人工审批 | 根据影响范围和仓库规则确定评审者 | 方向是否正确，证据是否充分，剩余风险由谁承担 |
| 合并与渐进发布 | 在合并队列中验证改动与最新主线的组合，通过后用功能开关逐步放量 | 组合后的代码与实际运行是否稳定 |
| 发布后恢复 | 监控异常，必要时关闭功能或回滚 | 恢复是否及时，事故是否转化为回归测试与流程改进 |

前六项覆盖验证、合并与渐进发布，第七项负责上线后的恢复。人工审批人数、可自动合并的范围由项目规则确定，视频中的低风险免审、高风险多人审批依赖其内部保护机制。要求人工审批时，由指定人员对具体提交批准。

## 2. 在项目中使用

1. **明确验收条件。** 写清需求、影响范围、比较基线和候选提交 SHA。例如“无效注册信息会显示错误，网络请求次数为零”。
2. **先执行验证。** 开发 Agent 运行仓库已有的测试与构建入口，保存实际命令、退出码、日志和必要截图。回归测试应能证明旧缺陷出现时会失败。
3. **独立评审。** 新开评审会话，提供验收条件、基线、候选 SHA 和证据。审查者读取对应版本及相邻调用链，开发者逐项修复或说明误报依据。
4. **配置合并条件。** 将项目必需的 CI 检查和审批要求配置到仓库保护规则。修复产生新提交后，对新 SHA 重跑受影响的检查，并按仓库规则重新审批。
5. **验证组合与发布。** 使用合并队列验证最终组合，准备功能开关、监控和恢复步骤，再按项目发布流程逐步放量。

使用 GitHub Actions 的合并队列时，必需检查的工作流还要监听 `merge_group`，保证队列生成的组合提交能够触发验证。[GitHub 合并队列配置](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)

已有多 Agent 工作台可以把开发、评审和测试设为独立任务，最终结论都对应同一个候选 SHA，详见[终端协作流程](智能体开发新需求.md)。

## 3. Claude Code 的评审入口

在目标项目目录运行 `claude`，进入需求分支对应的会话，再分别输入：

```text
/code-review
```

检查当前差异的正确性。也可指定 PR，例如 `/code-review high 1234`。

```text
/security-review
```

检查当前分支相对 `origin` 默认分支的安全风险，需要仓库存在 `origin` 且默认分支引用可用。使用前通过 `/` 菜单确认当前版本提供这些入口。评审意见、CI 结果和仓库审批规则共同决定能否交付。[Claude Code 命令参考](https://code.claude.com/docs/en/commands)

给 Codex、OMP 等其他评审 Agent 时，可以复用以下任务模板，替换尖括号中的内容：

```text
评审需求 <需求名>，验收条件为 <条件>，比较 <基线 SHA> 到 <候选 SHA>。
检查相关调用链、逻辑边界、安全风险和测试有效性。
每个问题给出文件位置、触发条件、实际影响及证据，并核实反例以排除误报。同类问题一次列全。
完整中文报告保存到 docs/reviews/<需求名>-review.md，注明评审 SHA 和未验证项。
聊天只返回摘要和文件链接。
```

## 4. 控制成本和反复修改

- **首次尽量查全。** 同类问题一次提出，修复后重点检查新增变更及其影响范围，已解决的问题保留处理记录。
- **设置收敛点。** 连续三轮仍未解决时，人工复核方案、验收条件和评审标准，再决定下一步。
- **按风险增加审查。** 先用一个开发 Agent 和一个独立评审 Agent，高风险改动再增加专项复核。多 Agent 搜索和核实会增加模型调用成本。
- **让结果可追溯。** 交付记录包含最终 SHA、评审问题处理情况、测试命令与结果、恢复方式及负责人。

人负责判断需求方向、审核证据并承担交付责任。流程效果可通过评审耗时、返修次数、回滚率和事故情况持续检查。
