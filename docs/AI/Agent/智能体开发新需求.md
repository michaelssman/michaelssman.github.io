# 智能体开发新需求

## AI 智能体在开发中的角色

在真实项目中，AI 通常分 4 类角色：

1. **需求理解/拆解 Agent**
   - 把 PRD → 技术任务列表
   - 输出接口、模块、边界条件
2. **代码生成 Agent**
   - 写 feature code / patch
   - 生成 API / service / UI
3. **测试 Agent**
   - 生成单元测试 / 集成测试
   - 补边界用例
4. **代码审查 Agent**
   - review PR
   - 找 bug / 性能问题 / 安全问题

------

## 推荐流程

### Step 0：明确需求（Human + AI）

输入：

- PRD / 用户需求 / issue

让 AI 做：

- 需求拆解
- 技术影响分析
- 不确定点列表

👉 输出物：

- 功能列表
- API 设计草案
- 修改文件范围

------

### Step 1：任务拆解（AI 最擅长）

让 AI 输出：

- 需要改哪些模块
- 每个模块做什么
- 依赖关系
- 风险点

👉 例子：

```
新增订单导出功能
- backend:
  - order service 增加 export API
  - query 优化（分页+筛选）
- frontend:
  - 新增导出按钮
  - loading + download handler
- infra:
  - 文件存储 / 临时文件清理
```

------

### Step 2：代码生成（分块执行，不要一次性生成）

关键原则：

> 要拆成“小 patch + 可 review 单元”

做法：

- 每个模块单独 prompt
- 限定文件范围
- 限定 diff 风格输出

------

### Step 3：自动生成测试

让 AI：

- 根据代码生成 unit test
- 补 edge case

例如：

- 空数据
- 并发请求
- 超长输入
- 权限异常

------

### Step 4：AI Code Review

让另一个 AI agent 做：

- 找 bug
- 检查逻辑漏洞
- 安全检查（SQL injection / XSS）
- 性能问题

👉 很重要的一点：

> review agent 必须和 coding agent 分离（类似双人审查）

------

### Step 5：人类合并 + CI验证

最终：

- 人 review PR
- 跑 CI
- 再由 AI 辅助 debug failing test

------

## 终端工作流：并行评审与自动测试

### 日常从哪里开始

做 Java + Flutter 跨仓需求时，在 Ghostty 打开 Herdr，选 `app-management` 工作区，在其中一个终端启动 Codex CLI。这里已有 `product`、`designer`、`backend`、`flutter`、`reviewer` 五个角色，主 Agent 最多同时派三个子任务。你在这个终端提需求、审核产品方案和原型、最后验收。旁边可以开一个终端看差异或测试日志。[Java 与 Flutter 多 Agent 协作配置](Java与Flutter多Agent协作配置.md)

| 需要做的事 | 谁来做 | 什么时候用 |
| --- | --- | --- |
| 拆任务、对齐接口、收结果 | Codex 主 Agent | 全程只设一个协调者，优先复用现有的迭代和验收记录。 |
| 改代码、补用例 | `backend`、`flutter` | 确定前后端契约后可并行。纯 Flutter 改动只派 Flutter 开发者。 |
| 独立检查 | 现有 `reviewer`，或单独的 OMP 会话 | 日常先用 `reviewer`。需要第二种模型时，让 OMP 用已接入的 DeepSeek 审同一份改动。 |
| 跑测试 | 本地 Maven、Flutter 工具 | 主 Agent 在开发完成时调用，测试结果由命令、用例数和日志决定。 |
| 看多个分支的差异、跟踪跨回合的任务依赖 | Orca | 分别添加 Java 和 Flutter 的 Git 仓库。需要可视化编排时，由 Orca 内的协调会话接手这一轮派工。 |

### 怎样一边开发一边审核

1. 将需求拆成能单独验收的小块。例如注册页先做“输入无效时显示提示并且不发请求”，再做“请求失败后保留输入并允许重试”。第一块完成即可送审，开发者继续第二块。
2. 交给审核者四样东西：本轮验收条件、仓库和基线、固定版本的完整差异、已有测试证据。有已授权的阶段提交就用 SHA；尚未提交时，由主 Agent 保存带编号的审查快照，包括已暂存和未暂存的差异、新增文件和相关本地用例。审核者针对这一版指出文件、触发条件、影响和复现办法。保持同一份业务文件只有一位写入者。
3. 想让 DeepSeek 复核时，由协调者显式把上述材料交给独立 OMP。手动使用时在 OMP 中用 `/model` 选择已接入的模型。要省去来回复制，协调者也可在**审查快照目录**运行下面的单次调用，把模型返回的意见交还开发者。先把四项材料放入快照，模型名替换为本机实际可用的标识。OMP 自带的 Advisor 只跟随所在的 OMP 会话。[OMP 独立验收示例](../OMP/Advisor审查与测试验收.md)

```bash
omp --print --no-extensions --tools read,grep,glob --model '<供应商/模型>' \
  '读取此目录的验收条件、变更与测试证据。报告可复现的问题、文件位置和未验证项。'
```

### 交给 DeepSeek 审代码并运行测试

Codex 和 OMP 的 DeepSeek 会话各有自己的上下文。管理者可以用现有的 Codex 主 Agent。开发子 Agent 交回结果时，管理者把下列信息整理成一份临时交接单，让 DeepSeek 读交接单、查同一版源码，在对应目录运行测试。你只需在主会话提需求和看结果。

| 交接单要写什么 | 注册页示例 |
| --- | --- |
| 用户批准的目标、验收条件和关键决定 | 密码不合规时在字段旁提示，注册请求次数应为零。保持现有后端接口。 |
| 去哪里看代码，这次审哪一版 | 写明仓库与模块目录、基线和目标 SHA。含未提交改动时注明快照编号、完整差异及新增文件。 |
| 怎样验证，有哪些尚未确认 | 指出本地表单测试路径、测试命令、所需环境及未测的设备。附开发者的复现步骤和已有日志，供审核者独立核验。 |

只交付这次审测需要的材料。交接单和日志中使用测试数据，去掉密钥、真实手机号等敏感值。下例由**管理者在终端执行**，将两个路径替换成实际位置。本机 OMP 配置中的默认模型为 `deepseek/deepseek-flash`。

```bash
review_dir='/替换为待测版本的工作目录'
handoff='/替换为本轮临时目录/handoff.md'
omp --cwd "$review_dir" --model deepseek/deepseek-flash \
  --print --no-session --no-extensions --tools read,grep,glob,bash \
  "读取交接单 $handoff 和适用的项目规则。独立审查差异并运行指定的本地测试。保持业务源码不变。返回版本、问题位置、实际命令、退出码、用例数和日志位置；缺少证据的项标为未验证。"
```

`bash` 让 DeepSeek 通过 OMP 调用本地 Maven 或 Flutter 测试工具，也具备写文件的能力。`--cwd` 只指定起始目录，实际读写权限由运行环境控制。管理者收到输出后，按测试报告核对用例数和结果，再将问题交回 Codex 修复，重走一次交接。OMP 的退出码只说明这次模型调用的状态，测试命令有自己的退出码。

### 怎样做到开发完成就测试

**以开发者交回一版可测成果为触发点。** 主 Agent 保持会话运行，收到完成回报后立即执行对应命令，同时派独立评审。测试失败就把失败用例和日志交回开发者；修复后按新版本重新测试和复核。Java 与 Flutter 跨仓交付时分别记录版本，并对涉及的接口执行一次联调。

| 改动 | 测试工作目录 | 实际运行 |
| --- | --- | --- |
| Java 用户服务 | `java_demo/hhjava`，使用 JDK 17 | `mvn -pl hhjava-service/hhjava-user -am test`；其他服务替换为实际模块。 |
| Flutter 主 App | `flutter_demo/flutter_01` | 依赖就绪后运行 `flutter analyze` 和 `flutter test`。修改公共包时，在 `flutter_package` 也运行对应检查。 |
| 涉及页面、设备或跨端交互 | 对应 App 和测试环境 | 按已批准的验收条件补模拟器或真机验证。例如点两次注册，只发出一次请求。 |

这两个仓库按项目约定只在本地维护测试。新 worktree 或干净的 CI 环境可能缺少用例。优先在有可信用例的本地工作目录运行，测试期间暂停该目录的代码修改；需要持续并行时，把相同版本的代码和对应本地用例准备到独立测试目录。交付记录要写清代码版本、测试入口、实际用例数、退出状态和失败或跳过项。零用例或缺少测试副本时标为“未验证”。

其他项目沿用各自的验证入口。例如课堂 iOS 项目可以在仓库根目录运行 `python3 AccCollege/Scripts/run_business_response_tests.py` 验证业务返回解析，涉及页面或宿主集成时再补模拟器测试。评审结论交给主 Agent 汇总；项目要求独立报告时，可保存到 `docs/reviews/<需求名>-review.md`。

如果使用 Orca 编排，可将“最终评审”和“最终测试”都设为依赖开发任务。协调者收到成功的 `worker_done` 后，用 `orca orchestration task-list --ready --brief` 找到就绪任务，再用 `worker-start` 分别派发。创建依赖只会使任务进入就绪状态，仍需活跃的协调者派发。上面的本地流程也依赖主会话，关闭后要靠独立运行器或 CI 才能继续自动触发。[Orca 官方编排说明](https://orca.dev/docs/cli/orchestration) · [本地编排指南](../Orca/orca-orchestration-zh-CN.md)

### 可以直接发给主 Agent 的任务

```text
本轮目标：改进注册页，让用户能理解输入错误并顺利重试。
你负责协调。先按 app-management 的规则给我产品方案和验收条件，
批准后给我可点击原型，原型通过后进入开发。
把开发拆成可独立验收的小块。每块完成就给 reviewer 一份固定快照，
让开发者继续下一块。开发完成后直接运行受影响模块的本地测试。
发现问题就交回实现者修复，按新版本复测；缺用例或环境就明确标出。
最后给我可运行的页面、审核结论、实际测试数和仍需我决定的问题。
```

## 主流使用方式（方法论）

### PR Agent 模式（推荐）

流程：

1. issue → AI拆解
2. AI生成 branch + code
3. AI自动开 PR
4. AI review + test
5. 人 review merge

工具思路：

- GitHub Actions + AI bot
- PR reviewer agent

------

### 多智能体（Agent Workflow，企业级）

典型结构：

```
Planner Agent → Architect Agent → Coding Agent → Test Agent → Review Agent
```

特点：

- 每个 agent 只做一件事
- 类似“软件工厂流水线”

适合：

- 大型项目
- 微服务系统
- 高频迭代团队

------

## 关键最佳实践（非常重要）

### 1. 不要让 AI “直接改整个项目”

让 AI 动手前，先确定问题属于哪个业务模块、涉及哪一层，再据此限定文件范围。分步修改，每一步都能从 Git diff 看出它解决了什么问题。架构是组织代码的方式。[视频原作《AI乱改项目？用架构设计解决！》](https://www.douyin.com/video/7694738600127555062)

**先按功能划模块，再按职责找层。** 例如首页、朋友页、消息页可以各自作为一个模块。在模块内部，可以用下表判断从哪里开始查。云相册涉及从服务器取数据，四层都用得上。只在本机打开和关闭的弹窗，通常看前两层就够了。

| 层 | 负责什么 | 从哪里排查 |
| --- | --- | --- |
| 视图层 | 显示按钮、弹窗、列表等界面元素 | 按钮占着位置却看不见，先查样式是否把它设成了透明。 |
| 交互逻辑层 | 处理点击事件和界面状态 | 按钮可见，点了却没弹窗，查点击事件是否更新了弹窗的显示状态。 |
| 业务数据层 | 根据用户身份和业务规则处理请求、返回数据 | 云相册弹窗应显示 1 张照片却显示 2 张，先看接口给当前登录用户返回了几条记录。 |
| 数据存储层 | 保存和读取持久化记录 | 如果接口已经返回了错误数量，再核对实际存了几条、查询取了哪些记录。如果接口返回正确，则回到客户端检查数据怎样显示。 |

**给 Codex 的示例提示词（Flutter 注册页）**

> 注册页的“提交”按钮可见，点击后没有弹出预期的提示。请沿着按钮、点击回调、弹窗显示状态这条路径定位原因，指出对应文件和证据。修复范围先限定在注册模块。如果需要改登录页也在用的组件，先列出调用位置和可能影响。完成后验证注册页能弹出提示。如果改到了共享组件，也验证登录页原有行为。

------

### 2. 让 AI 输出“计划”比写代码更重要

80%价值来自：

- 设计
- 拆解
- 风险识别

------

### 3. 用“测试驱动 AI”

流程：

```
先让 AI 写 test → 再写实现
```

效果：

- bug 大幅减少

------

### 4. 给 AI 提供“项目上下文”

必须喂：

- 目录结构
- API规范
- coding style
- 现有模块说明

否则质量会很差

------

### 5. 每个 agent 单职责

不要一个 AI：

> 又写代码 + 又 review + 又测试

会互相污染判断

------

## 实战流程模板（你可以直接用）

你可以这样用 AI：

### ① 输入需求

```
帮我实现 xxx 功能（附 PRD）
```

### ② 让 AI 输出：

- 技术方案
- 文件修改清单
- 风险点

### ③ 再问：

```
请按模块逐个生成 patch（不要一次性输出）
```

### ④ 再问：

```
为每个模块生成 unit test
```

### ⑤ 再问：

```
review 这段代码，指出 bug 和优化点
```
