# DeepSeek Super-agent 如何同时跟进多项工作

当一个 Agent 在改登录页、另一个在补测试、第三个等你确认文案时，最费心的往往是把新反馈送给对的人，并记住哪件事卡住了。DeepSeek 提出的 Super-agent 把这部分协调工作交给系统，人负责给目标、定权限、做决定和验收。[抖音原视频](https://www.douyin.com/video/7707116311817620755) · [DeepSeek Harness 团队的设计原文](https://www.bilibili.com/opus/1265361021143351318)

## 什么时候适合用

| 遇到的问题 | 合适的组织方式 |
| --- | --- |
| 一项需求需要设计、编码、测试配合 | 用 Agent Team 拆分这一项需求，由主 Agent 协调子任务。 |
| 几项独立工作同时推进，消息又分散在群聊、Issue 和 PR 里 | 用 Super-agent 统一接收反馈，分派到对应的任务。每项工作内部仍然可以使用 Agent Team。 |

个人助手（Personal Agent）描述的是服务对象。无论为一个人还是为团队服务，只要希望**跨渠道接着聊、多个任务互不阻塞、有价值的事件主动跟进、中断后能继续**，就会遇到这套架构要解决的问题。

## 一条反馈如何找到原来的任务

假设团队在飞书提出“修复登录页错误”，随后又在 GitHub Pull Request（PR）下补充“提示文案也改一下”。系统通过以下对象把两次沟通连起来。

| 对象 | 在这个例子里的作用 |
| --- | --- |
| Trigger（事件） | 群里的修复请求、PR 下的新评论各是一次事件。 |
| Thread（讨论串） | 群消息及其回复属于一段讨论；PR 及其评论属于另一段。 |
| Router（调度层） | 判断请求是否可以受理，是新工作还是已有任务的反馈，并把相关信息交给负责的执行者。 |
| Ticket（工单） | 持续记录“修复登录页”这件事的来源、授权范围、进展、结果和需要人决定的问题。 |
| Worker、Session（执行者与工作会话） | Worker 在这张工单的独立会话中读代码、修改、运行测试，并报告结果。其他工单可以同时推进。 |

当工单已订阅相关 PR 的讨论串，后续评论可以直接送到原 Worker，不必每次请 Router 重新派工。订阅提供上下文，工单的授权范围依然有效。例如“同步改提示文案”可能属于原修复范围，而“顺便把登录方式改成短信”需要重新评估。[原型的领域模型与订阅规则](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/001-domain.md)

## 怎样控制主动性、上下文和中断恢复

- **何时主动。** 视频以活动报名转化率下降为例。先用规则过滤无关或重复的信号，再让模型结合背景判断是否值得跟进。授权可以只覆盖“分析原因、起草建议”，调价或增加预算仍由负责人决定。
- **当前要记住什么。** Session 保存工作历史，模型每一步只能看到有限的上下文。用 **Inline & Spill** 把当前目标和已确认的要求放在眼前，长报告在外部保留全文，上下文中只放摘要和引用。需要追查时，用 **Chain of Recall** 从消息找到讨论串、关联工单，再找到当初确认的要求。
- **怎样接着做。** 单独保存工单状态、已完成步骤、相关消息和待发送的回复。耗时任务可在后台执行，结果出来后再通知 Worker。中途又收到新要求，Worker 可以在下一步结合已有进度处理，进程重启后也有记录可供恢复。[原型的执行与恢复机制](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/003-execution.md)

## 怎么试用这套思路

1. 选一个目标清楚、验收简单的 Issue，例如“密码错误时显示指定提示，并补回归测试”。在任务里写清允许改什么、怎样验证、哪一步交人审核。
2. 在 DeepSeek 团队公开的研究原型中，一个实例对接一个 GitHub 仓库，飞书是可选入口。需要实际部署时，可请编码助手“阅读这个仓库的 `SETUP.md`，带我配置 dsh-superagent”，按仓库流程准备环境和账号。[原型说明](https://github.com/deepseek-ai/dsh-superagent-prototype) · [官方配置流程](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/SETUP.md)
3. 把推断任务的接单模式先设为 `observe`（默认）。此时可以检查系统遇到哪些信号、原本会接哪些工单，经授权的明确请求仍可正常执行。确认主动规则符合预期后，再决定是否切换为 `auto`。[接单模式与授权规则](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/002-authorization.md)
4. 在对应 PR 下补一条范围内的反馈，检查它是否回到原工单；再从管理面板找到等待人工输入的事项。验收时看 PR 改动、测试结果与待决定的问题，无需翻遍每个执行会话。

视频把跨设备运行和智能 Watchdog 列为进一步的设计探索。前者将计算、状态和工作环境分开，使本机休眠后仍能继续工作。后者从系统外判断任务是否卡住或反复绕圈。公开仓库提供的是研究原型，已展示事件接单、任务订阅、并行执行、状态保存与恢复。跨月记忆该保留哪些经验、多个 Worker 如何共享工具与权限、任务增多后 Router 如何扩展，以及跨渠道指令冲突时由谁裁决，仍是落地时需要解决的问题。[设计原文](https://www.bilibili.com/opus/1265361021143351318) · [公开原型的适用范围](https://github.com/deepseek-ai/dsh-superagent-prototype#dsh-superagent)
