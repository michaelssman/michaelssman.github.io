# 网关、认证过滤器与拦截器

如果还没写过 HTTP 接口，先完成 [Spring Boot 入门练习](../SpringBoot.md)。本文第 9 节用一个普通 MVC 拦截器观察执行顺序，再回头看真实网关的响应式安全链。

## 先认识网络和框架词语

| 词语 | 含义及作用 |
| --- | --- |
| 反向代理 | 客户端请求一个统一地址，代理替客户端访问后端并转回响应；网关是承担更多 API 治理职责的入口 |
| 路由（route） | “符合什么条件的请求转发到哪里”的规则，通常包含标识、目标地址、匹配条件及过滤器 |
| Predicate（断言） | 判断请求是否符合路由，例如 Path 根据 URL 路径匹配；不是修改请求的代码 |
| Filter（过滤器） | 处理请求或响应的一环，例如去前缀、写头、限流；不同框架的 Filter 接口不能混用 |
| 负载均衡（load balancing） | 多个服务实例可用时选择其中一个处理请求；不等于一个服务启动了多个 Java 类 |
| 服务发现 / Nacos | 服务上报实例地址，调用方按服务名发现它们；Nacos 还可提供配置管理，两种能力不能混为一谈 |
| Servlet | Java Web 请求与响应的标准 API；Spring MVC 建立在这一体系上，入口调度器称 DispatcherServlet |
| WebFlux / Reactor / Mono | WebFlux 是响应式 Web 框架；Reactor 提供其常用响应式类型；Mono 表示最多一个结果或完成/错误的异步序列 |
| JWT / JWKS | JSON Web Token 是带声明的令牌格式；JSON Web Key Set 是 JSON 密钥集合，本项目网关用其中公钥验签 |
| CORS（Cross-Origin Resource Sharing，跨源资源共享） | 浏览器根据服务器允许规则决定能否让页面读取跨源响应；Origin 由协议、主机、端口组成 |
| CSRF（Cross-Site Request Forgery，跨站请求伪造） | 借浏览器自动附带 Cookie 等凭据诱导发请求；不是跨域读取问题 |

SSO、OAuth2、OIDC、PKCE 及 scope 的基础解释见 [认证和授权的词语表](认证和授权.md)。先记住：网关验证请求携带的身份，用户服务负责核验密码并签发令牌，文件归属由业务服务判断。

## 1. 网关在系统中的位置

网关是客户端访问微服务的统一入口，可负责路由、跨域、入口安全和请求治理。它不承担用户注册等领域业务，也不替代下游服务的授权检查。

```text
App / 浏览器
    ↓
hhjava-gateway：可信转发头、CORS、路由、JWT 验签
    ├── hhjava-user：注册、登录、OAuth2/OIDC、唯一 RSA 签发方
    └── hhjava-backup-file：文件业务、自身 JWT 验签与业务授权边界
```

路由由外部 Nacos 配置参与决定。仓库可说明 `/user` 等路由约定，但不能据此宣称某台服务器已配置完成。

## 2. Filter、WebFilter、Interceptor 不要混用

| 机制 | 所属体系 | 常见用途 |
| --- | --- | --- |
| Servlet `Filter` | Servlet / Spring MVC | 请求进入 MVC 前后的过滤，Servlet Spring Security 过滤链基于此体系 |
| MVC `HandlerInterceptor` | Spring MVC Handler 执行链 | 围绕 Controller 执行做框架层处理，不代替完整安全过滤链 |
| WebFlux `WebFilter` | 响应式 Web 应用 | 在响应式请求链中处理请求，gateway 的转发头过滤器属于此类 |
| Gateway `GlobalFilter` / `GatewayFilter` | Spring Cloud Gateway 路由过滤链 | 全局或特定路由的转发处理 |

当前 gateway 基于 WebFlux，使用 `SecurityWebFilterChain`；user/backup-file 基于 Servlet，使用各自的 Servlet 安全配置。不要把 Servlet 的 ThreadLocal 用户方案直接复制进响应式网关。

### 请求进去、响应回来时的顺序

下面是同步 MVC 请求的简化顺序，异常和异步处理还存在各自分支：

```text
Servlet Filter 前置
  → DispatcherServlet 找到 Controller
    → Interceptor.preHandle
      → Controller → Service
    ← Interceptor.postHandle（正常处理返回后）
    ← Interceptor.afterCompletion（MVC 本次处理收尾）
← Servlet Filter 中 chain.doFilter 返回后的逻辑
```

`preHandle` 返回 true 才继续；返回 false 表示拦截，应明确处理响应。只有成功完成前置阶段的拦截器才有相应收尾调用；不要假定失败、异步等情况始终等同于同步成功路径。对于直接写 JSON 的 Controller，postHandle 时响应可能已提交，不适合再修改响应头。[Spring MVC 拦截器说明](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-config/interceptors.html)

响应式链的 `chain.filter(exchange)` 返回的是 Mono，不是已经完成的远程响应。需要用 `then`、`doFinally` 等响应式组合表达后置处理；直接写在方法调用下一行，不代表等请求完成后再执行。GlobalFilter 的顺序由路由链中的排序决定；它与 WebFilter 是不同链，不能只比较两个 `@Order` 数字就断言跨链先后。

ThreadLocal 是线程局部存储，值绑定线程而不是某个用户。线程池复用时不清理会污染后续请求；响应式请求可能跨线程执行，所以 gateway 使用响应式安全上下文，不能依赖手写 ThreadLocal 传用户。

## 3. JWT 验证交给资源服务器支持

客户端调用受保护 API 时发送：

```http
Authorization: Bearer <Access Token>
```

gateway 的 `SecurityConfig` 配置 OAuth2 Resource Server，框架解码器通过 JWKS 取得公钥并执行验证。自己拆开 JWT 的 Base64 内容只能读取声明，不能证明令牌可信。[Spring Security 响应式 JWT 资源服务器文档](https://docs.spring.io/spring-security/reference/reactive/oauth2/resource-server/jwt.html)

当前共同契约包括 RS256、issuer、audience、令牌时间，以及 scope/角色转换。gateway 不持有 RSA 私钥；user 与 backup-file 的资源接口仍独立验签。

不要通过“网关写一个 username Header，下游无条件相信它”取代下游身份验证。也不要因为网关已经认证，就忽略备份对象归属：当前文件业务仍需完善对象级授权，网关不能替它自动完成。

## 4. 公开端点为什么要精确匹配

gateway 对以下 JSON 接口只放行明确的 POST：

```text
/user/auth/register
/user/auth/mobile/login/password
/user/auth/mobile/token/refresh
/user/auth/mobile/logout
```

OAuth2/OIDC、JWKS、浏览器登录及协议退出相关入口也需要允许请求到达 user，例如 `/user/oauth2/**`、`/user/.well-known/**`、`/user/login`、`/user/connect/logout`。文档等其他白名单以 `SecurityConfig` 为准。

`permitAll()` 只表示不要求先通过网关的访问授权条件，不意味着用户认证、客户端认证或 PKCE 被关闭。移动端登录校验密码，刷新/退出校验对应会话凭据；未来增加的 `/user/auth/mobile/...` 路径不会因一个通配规则而自动公开。

对公开入口也不要自动附带无效 Bearer Token：资源服务器可能在路径授权前处理它并拒绝请求。注册和移动登录调试时，应清除继承的 Authorization。

## 5. 401/403 怎样返回 JSON

`CustomAuthenticationHandler` 只实现两个接口：

- `ServerAuthenticationEntryPoint`：认证缺失或失败时返回 401。
- `ServerAccessDeniedHandler`：认证成功但权限不足时返回 403。

认证成功继续执行请求链并路由到目标服务，不由网关提前返回一个“登录成功”响应，因此不需要认证成功回调。

处理器从 Spring 注入 `ObjectMapper`，在创建 Bean 时复制一次配置，生成只供网关错误响应使用的 `ObjectWriter`。它保留省略空 `data` 的契约，不修改全局 JSON 策略。

以下为响应写入方法节选：

```java
response.setStatusCode(status);
response.getHeaders().setContentType(MediaType.APPLICATION_JSON);
return Mono.fromCallable(() -> responseWriter.writeValueAsBytes(
                ResponseResult.error(status.value(), message)))
        .flatMap(bytes -> {
            DataBuffer buffer = response.bufferFactory().wrap(bytes);
            return response.writeWith(Mono.just(buffer));
        });
```

`Mono` 表达异步完成或错误，`DataBuffer` 承载响应字节。`writeValueAsBytes` 生成 UTF-8 JSON，序列化失败沿响应式错误链传播，不被吞掉。不能在这里使用阻塞式业务查询。

例如未认证返回 HTTP 401 和：

```json
{"code":401,"message":"未认证或认证已过期"}
```

OAuth2/OIDC 下游协议端点保持标准错误格式。Servlet 业务异常由另一套公共处理器处理，详见 [异常处理](../异常处理.md)；JSON 基础见 [序列化](../序列化.md)。

## 6. 转发头与重定向安全

`Forwarded`、`X-Forwarded-Host`、`X-Forwarded-Proto` 等请求头会影响下游生成的地址。客户端可以伪造这些头，不能直接信任。

当前 `GatewayForwardedHeaderFilter` 在安全链和路由前完成：

1. 对 `/user` 路由检查请求协议、Host 和端口是否与配置的公开 issuer Origin 一致，不一致返回 400，不重定向。
2. 删除客户端携带的常见转发头。
3. 继续请求链，由 Gateway 根据已校验的连接信息重建转发头。

这使 user 能生成正确的外部登录和授权地址。Origin 指协议、主机、端口，不包含 URL 路径。

当前设计把 gateway 视为第一层可信代理。如果前方再加入负载均衡器或 TLS 终止代理，需要另行设计可信网络来源和代理适配，不能直接恢复对所有公网转发头的信任。

## 7. CORS 与 CSRF 各解决什么

gateway 针对 `/user/**` 配置精确 SPA Origin、允许的方法和请求头，并允许携带凭据。这个条件下不能把 Origin 改成 `*`。CORS 是浏览器跨源读取约束，不是 App/脚本访问控制，也不验证用户身份。

gateway 的无状态资源安全链关闭 CSRF，不代表 user 可以关闭。user 的浏览器登录依赖 Cookie/Session，必须保留 CSRF；仅注册和三个明确的无状态移动 JSON 端点精确豁免。

PKCE、CORS、CSRF 分别处理不同风险，不能相互替代。通用概念见 [OAuth2/OIDC 学习笔记](OAUTH2_OIDC_VIDEO_STUDY_NOTES.md)。

## 8. 改动后怎样检查

在 hhjava 根目录执行：

```sh
mvn -pl hhjava-gateway -am test
```

检查 401/403 状态与 JSON、中文和空字段契约、公开 POST 精确匹配、错误 Token、CORS Origin，以及伪造转发头与不合法 Host。

本地测试不验证远端路由已经存在。真实联调还要确认 Nacos 路由、下游可达性、JWKS/issuer/audience 一致性，并检查浏览器登录重定向和携带凭据的跨域请求。

## 9. 动手：用响应头验证 MVC 拦截器确实执行了

这是**普通 MVC 学习实验，不是网关认证方案**。前置：完成 [Spring Boot 第 9 节](../SpringBoot.md)，操作在 Mac 的独立 `hhjava-learning-basics`；无需新增依赖，不添加 Spring Security Starter。

### 9.1 写拦截器

文件：`src/main/java/com/example/learning/web/LearningInterceptor.java`

```java
package com.example.learning.web;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.web.servlet.HandlerInterceptor;

public class LearningInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response,
                             Object handler) {
        // 只证明这个教学拦截器执行过，不能把此响应头当作身份或授权证明。
        response.setHeader("X-Learning-Interceptor", "visited");
        return true;
    }
}
```

不用为本练习读取 Authorization、比较密码或自行解析 JWT。handler 是被 MVC 选中的处理器；request/response 是本次请求响应，不是全局共享的用户对象。

### 9.2 注册到 MVC

文件：`src/main/java/com/example/learning/web/LearningWebConfiguration.java`

```java
package com.example.learning.web;

import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.InterceptorRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
public class LearningWebConfiguration implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new LearningInterceptor())
                .addPathPatterns("/hello", "/books");
    }
}
```

`WebMvcConfigurer` 用于补充 MVC 配置，注册后仅对这两条路径生效。不需要 `@EnableWebMvc` 接管整套 Boot MVC 配置，也不需要另外给拦截器加一个重复的 Bean 注册入口。

### 9.3 启动和验证

停止原学习进程，在学习工程根目录运行 `mvn spring-boot:run`，另开 Mac 终端：

```sh
curl -i 'http://127.0.0.1:18080/hello'
```

预期仍是 HTTP 200 与问候 JSON，额外出现 `X-Learning-Interceptor: visited` 响应头；HTTP 头名称大小写不敏感。Reqable 在响应 Headers 中查看，而不是在 JSON 中找这个字段。

文件：`src/test/java/com/example/learning/LearningInterceptorTest.java`

```java
package com.example.learning;

import org.junit.jupiter.api.Test;
```

## 10. 看懂真实网关路由，避免把教学规则写进 Nacos

在当前 hhjava 中，路由是外部配置的一部分。先在 gateway 的 `application.yml` 确认它导入的 Nacos Data ID、Namespace、Group，再打开对应配置，只查看现有目标与规则；文档不能代替你确认实际运行值。

例如读到 `Path=/user/**`、`StripPrefix=1`、`uri=lb://hhjava-user` 时，应逐项理解：

1. Path 匹配请求路径，不包含 Host；请求 `/user/auth/register` 符合条件。
2. StripPrefix=1 去掉第一个路径片段，转给 user 的路径成为 `/auth/register`，不是删除第一个字符。
3. `lb://` 表示通过负载均衡和服务发现解析服务名，不是 DNS 域名；它需要相应依赖、服务注册以及可达的实例地址。
4. 若实际 uri 使用 `http://...`，就是指定的目标地址，不能仅因为教程使用 lb 就认定它已启用服务发现。
5. 路由能转发不代表公开访问；安全链的 permitAll/认证/授权规则仍独立决定是否允许请求。

排障顺序：网关本身能否到达 → 路由是否匹配 → 目标实例是否存在且从网关机器可达 → 下游路径是否正确 → JWT 与业务授权是否通过。不要把 404 一律归结为“Token 错误”，也不要用公开所有路径解决 401。
