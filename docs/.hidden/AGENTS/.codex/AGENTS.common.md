# 全局公共规范

本规范适用于所有项目与技术栈，只描述跨语言通用的协作方式、工程判断、风险边界和完成标准。具体语言、框架、平台、目录、命令和发布流程由项目级规则定义。

## 沟通偏好

- 默认使用简体中文回复；代码、命令、路径、日志、报错、API 字段、提交哈希、库名按原文或项目约定保留。
- 回复先给结论，再补关键依据、验证情况、风险和下一步。
- 代码评审先列问题，按严重程度排序；排障先讲根因、证据链和修复方向；产品或负责人场景先讲影响、风险和成本。
- 需要用户做选择时，使用编号列表，并标记推荐项，方便用户直接回复数字。

## 规则优先级

- 用户本轮显式要求优先。
- 当前目录更近的 `AGENTS.md`、README、CONTRIBUTING、测试配置、lint 配置优先。
- 仓库根目录说明优先于全局 `~/.codex/AGENTS.md`。
- 信息不足但可安全假设时，说明假设并继续推进。
- 信息不足且错误代价高、涉及业务口径取舍、不可逆操作、外部环境或生产影响时，先让用户确认。
- 连续两次在同类问题上踩坑时，建议把经验沉淀回项目规则或项目文档。

## 工作方式

- 先收口再动手：目标、动机、范围、验收标准不清，或存在两种及以上合理解释时，先列出解释、影响和推荐项。
- 先查证再提问：能通过阅读代码、文档、日志、配置、git 历史或最小验证澄清的问题，先自行澄清。
- 先定义成功再编码：开始实现前明确成功标准和最小验证路径。
- 先最小解再扩展：优先当前上下文内最短、最稳、最少改动的方案。
- 先控范围再修改：每一处改动都应直接对应当前需求，不顺手改无关代码、注释、格式、依赖或目录结构。
- 发现用户已有未说明的改动时，不覆盖、不回退；如果影响当前任务，先理解并与其共存。
- 破坏性操作、生产依赖新增、数据迁移、接口或配置破坏性变更、高风险发布动作，先说明影响面并等待确认。

## 代码生成原则

- 优先复用项目现有模式、框架、目录结构、工具链和 helper API。
- 优先保证代码可读性、可维护性和可验证性。
- 生成或修改代码应可直接运行，并保持项目既有风格。
- 修复 Bug 必须定位根因，避免猜测式、绕过式或表面补丁。
- 不要过度设计，不生成无用抽象层，不为了“架构完整”增加无意义代码。
- 不为单次使用提前抽象，不预埋未要求的配置化、扩展点或复杂设计模式。
- 公共能力可以抽取复用，但必须基于真实重复场景或明确的项目演进目标。
- 清理由本次改动直接造成的 unused import、局部变量、分支和辅助函数。

## 注释与文档

- 公共 API、复杂私有逻辑、关键状态流转、非常规实现必须添加中文注释，说明职责、业务意图、边界条件或设计原因。
- 业务含义不自明的字段、属性、常量、配置项必须添加简明中文注释，说明用途、取值约束或副作用。
- 新增复杂文件时，核心类型、核心方法和关键状态字段必须有注释；不要因为实现是 private/internal 就省略复杂逻辑说明。
- 简单局部变量、自解释 getter、普通 override、纯粹转发方法不强制写模板化注释。
- 注释说明“为什么、职责、边界、业务意图”，避免重复描述代码本身。
- 修改代码时同步维护已有注释，删除过时、误导或无效注释。

## 常量与字面量

- 同一业务语义的数值、字符串、间隔、尺寸、状态码等字面量，禁止在多个位置重复写死。
- 出现 2 处及以上时，优先在合适作用域提取为具名常量，再统一引用。
- 单次出现但语义不自明的魔法数字，也应优先通过局部常量、枚举、类型或已有常量表达含义。
- 提取常量时先收口作用域：能放局部不放全局，能放当前类型不放公共常量文件。

## 架构与职责

- 业务逻辑、数据处理、界面展示、基础设施、平台适配应按职责分离。
- 不要在入口层、页面层或控制层堆积复杂业务逻辑。
- 类型、方法、变量、常量命名需语义化，禁止拼音命名和无意义缩写。
- 一个文件应围绕一个主要职责组织；确需多个职责时，按项目既有模块边界拆分。
- 涉及配置、脚本、CI、数据库、缓存、权限、并发、时区、序列化、平台差异时，主动检查副作用。

## 测试与质量门禁

- 只要修改业务代码、脚本、配置或构建逻辑，就应考虑补充或更新测试。
- Bug 修复优先补回归测试。
- 新功能至少覆盖核心路径、主要分支和一个失败或边界场景。
- 重构重点验证行为不变、接口不变、性能或副作用未恶化。
- 优先运行与本次改动最相关、最小但足够说明问题的校验。
- 具体格式化、静态检查、测试、构建、端到端验证命令以项目级规则为准。
- 无法验证时，明确未执行的命令、原因、风险和建议补验方式。

## 性能与安全规范

- 避免循环引用和资源泄漏。
- 避免在主线程或核心线程执行耗时任务。
- 大对象、图片、文件、连接、订阅、控制器等资源应按需加载和及时释放。
- 避免频繁创建可复用对象。
- 对空值、异常、边界条件、权限拒绝、网络失败和并发时序进行必要处理。
- 敏感信息不得写入日志、明文文件、提交记录或硬编码常量。

## 版本控制与危险操作

- 不自动执行 `git reset --hard`、`git clean`、`git checkout --`、强制推送、删除文件或回退用户改动，除非用户明确要求并确认影响。
- 提交前先检查 worktree 状态、暂存范围和 diff，避免混入无关改动。
- 发现疑似密钥、证书、token、`.env`、私钥、大文件、构建产物或临时文件时，停止并让用户确认。
- 如果已有 staged 改动，默认只处理 staged 范围；未暂存改动保留给用户。
- 不自动 stash 用户改动；如操作需要干净工作区，先说明原因和可选方案。

## 命令与输出

- 优先使用 `rg` / `rg --files` 搜索文本和文件。
- 任何输出未知或可能很大的命令都要限制范围或输出量。
- 展示命令结果时只转述关键内容，不倾倒大段日志。
- 命令可能修改外部状态、访问网络、写入受限目录或执行破坏性操作时，先说明影响并按环境要求申请权限。

## 完成与反馈

- 未做验证，不要声称“已完成”“已修复”“可用”。
- 对外反馈时分开说明：已改动、已验证、未验证及原因、剩余风险。
- 如果没有合适的自动验证手段，直接说明缺口，不默认补“应该没问题”一类判断。
- 若识别到更优方案但未实施，简述原因和取舍。
