## 小木记账：基金多数据源行情模块

### 简历原句

> 持续迭代基金多数据源行情模块，统一净值、盘中估值、场内行情与持仓推算口径；实现并发限流、SQLite 分层缓存、请求去重、新鲜度校验、失败降级及待处理交易补算。

### 30 秒回答

基金模块的难点不是请求单个接口，而是不同数据源的含义和更新时间不一致。我把行情拆成官方净值、盘中参考和场内实时三层，通过统一的 `FundBabyQuoteResolver` 结合交易日、数据日期和更新时间选择最终行情，使列表展示、排序、资产汇总和收益计算使用同一口径。请求侧限制最多 4 个并发，详情请求支持 3 分钟缓存和进行中任务去重；持久化侧使用 SQLite 四表，列表只增量更新摘要，详情才更新重仓股和历史走势，接口失败时继续使用当前快照。

### 2 分钟回答

基金数据同时包含正式净值、第三方盘中估值、ETF/LOF 场内价格以及根据前十大持仓推算的估值。如果让每个页面自行选择字段，很容易出现列表显示盘中估值、排序使用官方净值、资产汇总又使用场内价格的问题。

我的处理方式是先在模型层明确三种行情层级，再由统一解析器根据业务上下文选择最终结果。场内基金存在当天成交价或 IOPV 时优先使用场内行情；场外基金只有在交易日、09:00 后、官方净值尚未更新到当天且盘中数据属于当天时，才使用盘中参考。如果第三方估值缺失，可以使用前十大持仓的加权涨跌幅推算，但有效行情覆盖率必须达到 50%。官方净值更新到当天后，正式净值重新成为最终口径。

网络请求分为列表轻量刷新和详情完整刷新。列表只请求当前分组可见基金的摘要行情，最多同时处理 4 只；详情才加载重仓股、行业归因、近 90 日走势和分时曲线。同一基金正在刷新时，后续调用复用同一个 `Future`。接口失败时保留旧快照，非关键的分时和行业补齐不阻塞主列表。

持久化使用独立 SQLite 数据库，拆成摘要、重仓股、历史走势和缓存元数据四张表。列表刷新只更新摘要行，详情刷新通过事务更新单只基金及其子表；完整分时曲线只保存在内存。当前阶段不兼容旧版 SharedPreferences 基金快照，新安装直接以 SQLite 空库作为数据起点。

### 一、为什么需要统一行情口径

同一只基金在同一时刻可能同时存在多种数值：

| 行情层 | 主要数据 | 更新特点 | 用途 |
| --- | --- | --- | --- |
| 官方净值 | 单位净值、净值日期、正式涨跌幅 | 通常交易日结束后确认 | 历史收益和最终确认口径 |
| 盘中参考 | 第三方估值、估值时间、持仓推算结果 | 交易时段内变化 | 场外基金盘中收益参考 |
| 场内实时 | ETF/LOF 最新成交价、IOPV、行情时间 | 交易时段内变化 | 场内基金实时市值 |

这些数值不能直接混用：

- 官方净值可靠，但盘中尚未更新。
- 第三方估值及时，但属于估算结果。
- 持仓推算只覆盖已披露的主要持仓，不代表完整投资组合。
- ETF/LOF 的成交价反映交易价格，与场外基金单位净值不是同一口径。

因此页面不直接读取某个行情字段，而是统一消费 `FundResolvedQuote`，其中包含行情层级、最终值、涨跌幅、时间、来源及是否为估算值。

### 二、模块职责划分

| 类型 | 职责 |
| --- | --- |
| `FundBabyController` | 协调页面状态、远端服务、本地存储、分组、持仓和交易队列 |
| `FundBabyApiService` | 聚合净值、估值、场内行情、重仓股及历史走势数据 |
| `FundBabyQuoteResolver` | 统一行情选择、新鲜度判断和收益计算口径 |
| `FundBabyListRefreshService` | 执行当前可见列表的轻量行情刷新 |
| `FundBabyDetailCache` | 管理 3 分钟详情 TTL 和 in-flight 请求去重 |
| `FundBabyConcurrency` | 使用固定工作池限制批量请求并发数 |
| `FundBabyStorage` | 对控制器提供统一存储入口，区分完整同步、摘要更新和详情更新 |
| `FundBabyCacheDatabase` | 负责行情 SQLite 建表、事务、增量读写和级联删除 |
| `FundBabyTradeService` | 计算买卖结果并补算待处理交易 |

### 三、行情选择和新鲜度校验

#### 1. 场内实时行情

场内基金只有在成交时间或 IOPV 时间属于当天时，才允许优先使用场内行情：

```text
当天场内成交价 > 当天 IOPV > 其他行情层
```

这样可以防止休市后仍把上一个交易日的价格标记成实时行情。

#### 2. 盘中参考行情

使用盘中参考必须同时满足：

1. 当前被判定为交易日。
2. 当前时间已经到 09:00。
3. 官方净值日期不是今天。
4. 盘中估值时间属于今天。
5. 估值数值有效；或者持仓推算覆盖率达到 50%。

盘中参考内部优先级：

```text
第三方盘中估值 > 覆盖率达标的持仓推算
```

官方净值一旦更新到今天，盘中估值不再覆盖正式结果。

#### 3. 最终选择顺序

在通过交易日和时间校验后，正常选择顺序为：

```text
当天场内实时行情
    ↓ 不可用
当天盘中参考行情
    ↓ 不可用
官方净值
```

如果官方净值也缺失，解析器会保留其余仍可展示的估算或场内数据作为最后兜底，避免页面直接显示空值，但 UI 仍展示对应来源和估算标识。

#### 4. 交易日判断

- 周六、周日直接判定为非交易日。
- 工作日结合上证指数行情日期进行校验。
- 指数日期是今天，判定为交易日。
- 日期不一致且已经超过 09:30，按节假日处理。
- 09:30 前允许指数接口尚未切换日期，暂按交易日处理。
- 指数接口不可用时，工作日采用可用性优先的默认策略，但行情本身仍要通过日期校验。

### 四、持仓推算逻辑

前十大持仓接口返回股票权重，再结合个股当日涨跌幅计算加权贡献：

```text
加权涨跌贡献 = Σ（持仓占比 × 个股涨跌幅）
持仓覆盖率   = 有有效行情的持仓占比之和 / 100
推算涨跌幅   = 加权涨跌贡献 / 100
推算净值     = 官方净值 ×（1 + 推算涨跌幅 / 100）
```

例如三只有效持仓的占比分别为 10%、8%、7%，有效覆盖率只有 25%，即使能够算出推算涨跌幅，也不会把它作为主行情展示。当前阈值为 50%，目的是避免少数股票的涨跌代表整只基金；低覆盖率结果只能作为辅助信息。

这套结果继续交给统一行情解析器，因此列表展示、涨跌幅排序、持有市值和收益计算不会各自重新选择价格。

### 五、收益计算口径

```text
持有市值 = 持有份额 × 统一行情值
持有收益 =（统一行情值 - 平均成本）× 持有份额
```

当日收益只在最终选中的行情确实属于当天时计算：

```text
当日收益 = 当前市值 - 当前市值 /（1 + 当日涨跌幅 / 100）
```

如果最终行情是旧的官方净值，不强行计算“今日收益”，避免用跨日数据生成错误结果。

### 六、并发控制、刷新范围和请求去重

#### 列表刷新

- 只刷新当前模块、当前分组中可见的基金代码。
- 使用固定工作池，最大并发数为 4。
- 列表接口只请求净值、盘中估值和场内行情等摘要字段。
- 重仓股、行业归因和历史走势沿用缓存，不跟随每次列表刷新重复请求。
- 缺失的行业归因在后台补齐，不阻塞列表主流程。
- 如果所有列表请求都失败，不执行无意义的数据库写入。

刷新过程中快速切换分组时，不并行启动多轮全量刷新，而是记录最后一次可见列表请求；当前任务结束后再执行最后一次请求，避免请求风暴，也避免新页面漏刷。

#### 详情刷新

首次请求详情时，同时启动完整详情和分时曲线请求。每只基金维护一份正在执行的 `Future`：

```text
第一个调用者创建远端任务并登记
后续同基金调用者发现已有任务
所有调用者等待同一个 Future
任务完成后在 finally 中清理登记
```

不同基金代码拥有独立任务，可以并行刷新；同一基金不会重复请求。

### 七、SQLite 分层缓存

#### 1. 数据库存在哪里

基金行情使用独立数据库文件：

```text
fund_baby_cache.db
```

文件由 `sqflite` 创建在 App 的数据库目录中，不与普通记账账本数据库混用，避免业务表、升级策略和生命周期互相影响。

#### 2. 四张表

| 表 | 内容 | 更新方式 |
| --- | --- | --- |
| `fund_summary` | 基金身份、显示顺序、官方净值、盘中估值、场内行情、昨日涨跌 | 列表刷新时按基金增量更新 |
| `fund_holding_stock` | 前十大重仓股、权重、行业路径、个股涨跌 | 完整详情刷新时替换单只基金数据 |
| `fund_trend` | 历史净值时间戳、净值、涨跌幅 | 完整详情刷新时替换单只基金数据 |
| `fund_cache_meta` | 摘要时间、详情时间、持仓时间、走势时间、Schema 版本 | 与相应数据在同一事务更新 |

重仓股、历史走势和缓存元数据通过外键关联 `fund_summary`，删除基金摘要时由 SQLite 级联删除子表数据。

#### 3. 三种写入路径

列表行情刷新：

```text
网络返回成功的基金摘要
    ↓
只 UPDATE 对应 fund_summary
    ↓
只更新 summary_updated_at
    ↓
不触碰重仓股和历史走势
```

详情刷新：

```text
BEGIN TRANSACTION
更新单只基金摘要
删除并重建该基金重仓股
删除并重建该基金历史走势
更新详情缓存时间
COMMIT
```

添加、删除、清空和持有列表重排属于低频操作，以当前基金列表为完整事实源执行事务同步。对于已经存在的基金，单纯重排不会把缓存时间伪装成刚完成远端刷新。

#### 4. 为什么分时曲线不落盘

`intradayMap` 保存分钟级分时点，只在内存中存在：

- 分时曲线只对当前交易日有价值。
- 数据点多且更新频繁，持续落盘会产生额外 I/O。
- 跨日后旧曲线容易被误认为今天的数据。
- 分时属于增强展示，失败不影响净值、资产和收益主流程。

冷启动时如果 SQLite 详情仍在 3 分钟 TTL 内，系统不会重复请求重仓股和历史走势，但会单独补拉没有落盘的分时曲线。只有分时补拉成功后，当前进程才继续复用剩余的详情 TTL。

#### 5. 版本策略

当前阶段明确不兼容旧版基金缓存：

- 不读取或解析 SharedPreferences 中的 `fund_baby_funds`。
- 不维护迁移标记、一次性迁移任务或迁移失败兜底。
- SQLite 首次创建时使用空库，由当前业务初始化流程添加基金。
- 自选代码、分组、个人持仓和待处理交易等轻量状态仍保存在 SharedPreferences。

### 八、失败降级

按影响范围分级处理：

- 单只基金列表刷新失败：返回该基金旧摘要，其余基金继续更新。
- 全部列表刷新失败：保留当前列表，不重复落盘旧数据。
- 详情刷新失败：返回控制器或 SQLite 恢复的旧详情，不清空页面。
- 冷启动分时补拉失败：保留 SQLite 详情，下次进入时可以继续尝试。
- 主估值接口失败：组合官方净值、基金搜索、重仓股、历史走势和场内行情构建降级结果。
- 行业归因或分时增强失败：记录日志，不阻塞主列表。
- SQLite 的单只详情写入使用事务，避免摘要已经更新但持仓和走势只写入一部分。

### 九、待处理交易补算

基金买卖提交时，成交净值可能尚未公布：

1. 15:00 前提交，从所选交易日开始查找净值。
2. 15:00 后提交，从下一个自然日开始查找。
3. 最多向后扫描 30 天，自动跨过周末、节假日和净值未公布日期。
4. 暂时找不到净值时，不直接修改持仓，而是写入待处理交易队列。
5. 后续行情刷新时重新查询；成功的交易更新持仓，未成功的继续保留。
6. 可以只补算当前可见基金，避免每次刷新扫描全部队列。

买入计算：

```text
净买入金额 = 总金额 /（1 + 费率 / 100）
新增份额   = 净买入金额 / 成交净值
新平均成本 =（原平均成本 × 原份额 + 本次总金额）/ 新总份额
```

卖出时减少持有份额，份额归零后删除持仓。当前实现不扩展宣称完整的已实现收益和卖出费用核算。

### 十、测试覆盖

- SQLite 基金摘要、重仓股、历史走势和列表顺序往返恢复。
- 列表摘要增量更新不会清空已有重仓股和历史走势。
- 完整事实源同步可以删除已移除基金，并通过外键清理子表。
- 新 SQLite 空库不会读取或迁移旧 SharedPreferences 基金快照。
- 同一基金详情请求去重、3 分钟内存缓存和强制刷新。
- 冷启动命中 SQLite 详情 TTL 时只补拉分时曲线。
- 列表刷新只请求当前可见分组。
- 全部列表请求失败时保留旧快照且不重复持久化。
- 行情解析覆盖第三方估值、持仓推算覆盖率不足、旧估值拒绝和官方净值回退。

### 十一、常见追问

#### 为什么不把完整分时曲线也存入 SQLite？

分时曲线生命周期只有一个交易日，而且属于增强展示。内存保存可以减少频繁写入和跨日失效处理；冷启动只补拉分时，比重新请求全部详情成本更低。如果以后需要离线曲线，可以按“基金代码 + 交易日期 + 时间”建表，并设置跨日清理策略。

#### 为什么不用一张表保存整个 JSON？

单条 JSON 实现简单，但更新一只基金也要重写整个列表，无法独立管理摘要、持仓和走势的生命周期。分表后可以按基金增量更新、使用事务和外键级联，也能避免单条 JSON 损坏导致全部基金无法恢复。

#### 为什么详情缓存是 3 分钟？

详情中的持仓和历史走势变化慢，短时间重复进入没有必要重新请求；同时盘中行情不能缓存过久，所以使用较短 TTL。具体值是当前产品规模下的折中，不宣称它是所有场景的固定最优值。

#### 为什么列表刷新只更新摘要？

列表只需要当前价格、涨跌和少量身份信息。重仓股和历史走势数据更大、变化更慢，如果每次下拉刷新都重新请求并写入，会放大网络和数据库成本。

#### SQLite 写入是否完全原子？

单次基金详情和完整列表同步在一个 SQLite 事务内，相关四张表要么全部成功，要么全部回滚。SQLite 与仍保留在 SharedPreferences 中的其他用户状态不属于同一个跨存储事务，因此面试时不能表述为整个基金模块所有数据都具备数据库原子性。
